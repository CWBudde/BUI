Package `bui` drives BUI's widget tree from Go: create nodes, set their properties, lay them out and handle their clicks. By default it needs no C toolchain at all, so `CGO_ENABLED=0 go build` works for any operating system and architecture Go supports.

The binding is experimental, and the API is small and will change. On Linux and macOS it opens real windows through its own window hosts, written in Go, still with no cgo: **X11** on Linux and **Cocoa** on macOS. On every platform it also renders **headless**: into memory, with synthetic input, which is what tests and screenshots need. Windows has no window host yet, so there it renders headless only.

## Install it

You need Go 1.26 or newer. The module is `github.com/ppmpreetham/BUI/bindings/go`. It has no tagged release yet, so take it at a commit:

```sh
go get github.com/ppmpreetham/BUI/bindings/go@main
```

## A first tree

This builds a frame with one button, renders it, and clicks the button in the middle. It prints `clicked`:

```go title="main.go"
package main

import (
	"fmt"

	bui "github.com/ppmpreetham/BUI/bindings/go"
)

func main() {
	root := bui.NewNode("frame")
	defer root.Close()

	button := bui.NewNode("button")
	button.SetStr("text", "Add step")
	root.Add(button)
	button.Pack(bui.PackOptions{Fill: bui.FillX})
	button.OnClick(func() { fmt.Println("clicked") })

	view := bui.NewHeadless(root, 320, 120)
	defer view.Close()

	view.Render() // lays out the tree, so Rect is valid from here on
	x, y, w, h := button.Rect()
	view.Press(x+w/2, y+h/2)
	view.Release(x+w/2, y+h/2)
}
```

`NewNode` takes the kit's widget types (`frame`, `button`, `label`, `slider`, `text` and the rest). `SetStr` and `SetNum` set their properties by name, and `Pack` places a node with BUI's Tk-style geometry manager. `Headless` owns the raster: `Render` lays out and draws the tree, and `Press` and `Release` send a left-button click.

## A window

On Linux, with an X server or XWayland, `examples/counter` opens a window with a slider, a button and two labels, one of which a goroutine updates every second through `bui.Do`. It builds into a static binary:

```sh
cd bindings/go
CGO_ENABLED=0 go run ./examples/counter
```

On macOS and Windows it exits with `ErrNoDisplay`.

## Two engines

The same API runs on two engines. You pick one when you build:

| Build | Engine | Windows | Needs |
| --- | --- | --- | --- |
| Default, any platform | The kit as an embedded WebAssembly module, run by [wazero](https://github.com/tetratelabs/wazero) | X11 on Linux and Cocoa on macOS, through hosts written in Go. None yet on Windows: `NewWindow` and `Run` return `ErrNoDisplay` | Only Go |
| `-tags bui_cgo`, Linux | The kit itself, from the static libraries of BUI's CMake build | X11, and Wayland on request, through BUI's own hosts | cgo, a C and C++ toolchain, and that build |

Both engines draw the same pixels: the binding's tests compare them exactly.

**The WebAssembly engine** compiles the module at the first kit call, in about 0.2 to 0.3 seconds, and caches the result, so later starts take about 25 ms. On amd64 and arm64 it renders at about 2 to 4 times the native time: a dense full-HD frame, drawn and put on an X11 window, took about 13 ms on the laptop it was measured on. Other architectures fall back to wazero's interpreter, which is far slower and fit for tests rather than interaction.

**Its X11 host** is a port of BUI's `kit_window_x11.c` to Go, on the pure-Go X client [xgb](https://github.com/jezek/xgb). The module runs inside wazero's sandbox, where it can neither open a socket to the X server nor load libX11, so the window lives outside it, in Go. The host follows `Xft.dpi` and `BUI_UI_SCALE` as the C host does, and its key translation is tested against libX11's on 13 layouts. Text is always UTF-8.

**Windows on macOS** come from a Go port of BUI's Cocoa host, which reaches AppKit through [purego](https://github.com/ebitengine/purego) and the Objective-C runtime. In `bindings/go`:

```sh
CGO_ENABLED=0 go run ./examples/counter
```

The window has a menu, takes the mouse, scroll and keys, quits with Cmd+Q, keeps drawing while you drag its edge, and follows a move to a screen of another scale. It has no input method (IME) support, and a dead key is not composed with the next key, as in BUI's own Cocoa host.

**The cgo engine** links the libraries you build at the repository's root. You need the X11 headers (`libx11-dev`) for windows:

```sh
cmake -S . -B build -DBUI_BUILD_TESTS=OFF -DBUI_BUILD_EXAMPLES=OFF
cmake --build build --target bui_kit
cd bindings/go
go run -tags bui_cgo ./examples/counter
```

The cgo engine opens the same window through BUI's own X11 host. Both engines open X11 windows, through XWayland on a Wayland desktop; set `BUI_WINDOW_BACKEND=wayland` for native Wayland windows from the cgo engine.

## Threading

Call `bui.Run` from the main goroutine. Every call that touches the kit belongs on the UI thread: the main goroutine before and after `Run`, and your handlers and `Do` functions while it runs. Other goroutines hand work to the UI thread with `bui.Do`, the one function that's safe from anywhere.

## Limitations

- **No windows on Windows yet.** The default engine has window hosts for X11 on Linux and Cocoa on macOS only. On Windows `Supported` is false, and `NewWindow` and `Run` return `ErrNoDisplay`.
- **The Go X11 host is plainer than the C one.** It has the core X cursors, not the desktop's cursor theme, and no Compose or IME input: a dead key types its own character. Clipboard text past about 256 KiB, which X sends in parts (INCR), is refused both ways.
- **Software rendering only.** `Headless` draws into a CPU raster, and the WebAssembly engine has no GPU renderer.
- **No GPU, video, file browser or IME.** None of them is in the module, and the binding exposes none of them.
- **A WebAssembly trap ends the process.** After a fault inside the module its state is unknown, so the process ends with a message instead of returning an error. Running out of the module's 1 GiB of memory counts as such a fault.
- **Generic properties.** You set properties by name with `SetStr` and `SetNum`; there are no typed widget structs.
- **Images stay pending** on the WebAssembly engine, which has no worker threads to decode them. The API sets no image source today.
